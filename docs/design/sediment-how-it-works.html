읽는 법

다섯 개의 띠를 위에서 아래로

아래 그림 한 장이 기계 전체다. 위에서부터 캡처 · 증류 · 저장 · 서빙, 그리고 설계는 끝났지만 아직 웹훅이 물리지 않은 알림까지 다섯 개의 띠로 내려간다. 띠와 띠 사이의 굵은 화살표가 각 단계가 다음 단계에 넘기는 것이다.

숫자는 전부 설계 문서와 코드에서 그대로 옮겼다. “주기적으로” 대신 실제 cron 표현식이, “상위 몇 개” 대신 실제 상수가 적혀 있다 — */30 * * * *, RRF k=60, final K=6 같은 것들. 나중에 grep하게 될 값들이기 때문이다.

가까이 봐야 할 네 곳

그림이 한 줄로만 말하고 지나간 것들

포스터는 자리가 없어서 짧게 적었지만, 실제로 사람들이 되묻는 지점은 정해져 있다. 네 곳을 풀어 쓴다.

검색은 왜 튜닝 손잡이가 하나뿐인가

④ Serve · Retrieval core

BM25가 상위 30개, 벡터가 상위 30개를 각각 뽑고, RRF가 이를 합쳐 최종 6개를 남긴다. RRF는 두 아암의 순위만 쓴다 — 1 / (60 + rank). 점수 스케일이 전혀 다른 두 검색을 섞으면서도 정규화가 필요 없는 이유고, 그래서 만질 파라미터가 사실상 k 하나로 줄어든다.

v1에는 재랭커 모델이 없다. 질의당 비용이 붙기 때문이다. 대신 품질은 골든셋 recall@3로 지켜본다 — hypeproof-lab 27/40, kids-edu 5/10이 현재 기준선이다.

검색이 실패해도 답은 나온다

④ Serve · 폴백 사다리

임베딩 키가 없으면 embed()가 0벡터를 돌려준다. 검색 코드는 그걸 감지해 BM25 단독 + OR로 이어붙인 ts_query로 빠진다. BM25가 0건이면 벡터 단독, 둘 다 0건이면 “인용을 찾지 못했다”고 말한다.

마지막 칸이 핵심이다. 근거가 없을 때 지어내지 않고 없다고 답하는 것이 설계된 동작이다. 이 분기 덕분에 OpenAI 키를 교체하던 사고 중에도 시스템은 계속 살아 있었다.

[DONE]보다 저장이 먼저다

④ Serve · SSE 순서

SSE에서 [DONE]을 보내는 순간 클라이언트가 연결을 끊고, 서버의 async 제너레이터가 취소된다. 그 뒤에 놓인 코드는 실행되지 않는다.

그래서 순서가 고정돼 있다 — delta 토큰 → citation 이벤트 → assistant 메시지 저장 → query event → [DONE]. 저장을 마지막에 두면 답변은 화면에 잘 보이는데 새로고침하면 사라진다. 한 번 겪고 나면 잊히지 않는 종류의 버그다.

테넌트 격리는 두 개의 DB 역할로 갈린다

③ Store · RLS

curator_app은 RLS를 적용받으며 요청 핸들러가 쓴다. curator_service는 RLS를 우회하며 인제스트와 크론만 쓴다. 요청마다 set_config('app.tenant_id', :v, true)로 컨텍스트를 심는다.

여기에 경계 원칙이 하나 더 얹힌다 — lab_lib/나 applications/ 아래 어떤 파이썬 파일도 테넌트를 이름으로 참조할 수 없다. 판별법은 간단하다. 내일 새 테넌트가 가입하면, 내 변경은 코드 수정을 요구하는가 아니면 config 행 하나면 되는가.
